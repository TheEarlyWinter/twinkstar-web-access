HanaAgent 插件

星愿浏览器访问：让 HanaAgent 安全接入星愿浏览器

无需重新打开独立浏览器。插件连接你已经开启远程调试的星愿浏览器，复用现有登录态，在后台标签页完成动态网页读取、站内搜索、点击、输入与上传，同时保持令牌认证和插件自建标签页边界。

问题不在工具数量，而在浏览器环境是否正确

独立实例很干净，也很笨

每次重开环境、重新登录、重新踩坑。对需要登录态的网站来说，这不是能力问题，是入口问题。

静态抓取便宜，但经常走错路

很多内容平台、后台系统、招聘站、社媒站内搜索，并不适合先 Search/Fetch 再补救。

真正缺的是一个升级档

轻任务继续用 Hanako 原生 web 工具；复杂网页切换到接管现有 Chrome 的 CDP 模式。这才合理。

核心结构

这个插件做了什么

接入现有星愿浏览器

通过 CDP 连接用户日常使用的星愿浏览器，不强行拉起新的浏览器实例，已有登录态可以复用。

补齐真实动作

支持开标签页、读页、执行 JS、点击、输入、滚动、截图、上传文件、关闭标签页。

保留最小化站点笔记

成功读取后仅按域名保存成功状态、访问方式和文本长度，不保存页面标题或正文。

三个最常见的使用场景

读动态网页

当静态抓取读不到正文，直接进入浏览器读取真实 DOM。

站内搜索

像人一样进入平台，在站内完成搜索、跳转和判断，而不是在搜索引擎外面打转。

页面操作

点击、输入、滚动、截图、上传文件，这些都不是 fetch 能解决的问题。

适合什么，不适合什么

场景 建议 原因
官网、博客、文档、公开静态页面 优先 Hana 原生 web search / web fetch 更轻、更快、代价更低
登录后页面、JS 重页面、社媒站内搜索 切到星愿浏览器访问插件 静态工具经常天然无效
上传、发布、填写表单、多步交互 切到星愿浏览器访问插件 这是浏览器自动化问题，不是抓取问题

为什么没有去改 Hanako 内核

因为 OpenHanako 更新很快。直接改 core / server / desktop，短期看更“原生”，长期看一定变成维护债。这个项目选择按官方插件体系接入：

  • 不入侵 Hanako 主仓库
  • 跟随官方插件 API 演进，而不是跟着内核细节一起抖
  • 把浏览器增强、策略注入、经验沉淀收束在一个 full-access 插件里

安装方式

1. 打开星愿浏览器 2. 访问 chrome://inspect/#remote-debugging 3. 开启远程调试并接受授权提示 4. 在 Hana → 设置 → 插件 中安装本插件 5. 允许 full-access 插件 6. 先调用 twinkstar-web-access_browser_status 确认发现成功

FAQ

它会取代 Hanako 原生 web 工具吗？

不会。它是更重的一档。静态网页继续用原生工具，复杂网页再升级到这个插件。

它会不会抢我浏览器控制权？

默认不会。它只操作插件自己创建的标签页，不碰你原有标签页。

为什么要做站点经验沉淀？

因为网页自动化最贵的不是点击，而是每次都重新试错。经验层的作用是让第二次访问不再像第一次那么陌生。

一句话总结

星愿浏览器访问插件不会取代 Hana 原生联网能力。静态工具不适用时，它让 Agent 在用户真实使用的星愿浏览器中完成任务，并以令牌、代理端标签页校验和按需启动控制风险。
